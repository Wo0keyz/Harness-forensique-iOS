Documentation technique

Reproduire l'installation depuis une machine vierge, puis comprendre chaque composant.

Conventions Les valeurs propres à l'infrastructure sont remplacées par des repères : <IP_POSTE_ANALYSTE> (poste autorisé à joindre la machine), <INTERFACE> (interface réseau vers ce poste), <RESEAU_LOCAL> (ex. 10.0.0.0/24), <HOTE_ANALYSE> (nom ou adresse de la machine d'analyse), <utilisateur> (compte Unix). Aucun secret n'est reproduit. Les chemins de code renvoient au dépôt du harness, Wo0keyz/Harness-forensique-iOS (cloné sous le nom forensic-langgraph, commit fbb2702), et au serveur MCP, Wo0keyz/iLEAPP-MCP (branche feat/harness-provenance, commit 8221f33).

Vue d'ensemble

Le harness est un graphe LangGraph écrit en Python. Il lit une sortie iLEAPP à travers un serveur MCP en lecture seule, fait raisonner un modèle local servi par llama.cpp (API compatible OpenAI), contrôle chaque sortie du modèle par du code, et produit un rapport traçable dans un dossier d'exécution scellé. Quatre éléments, tous sur la même machine :

ÉlémentEmplacement de référenceRôle
forensic-langgraph~/forensic-langgraphLe harness (paquet forensic_harness), ses jeux d'évaluation, son infrastructure versionnée (infra/). Code : Wo0keyz/Harness-forensique-iOS.
iLEAPP-MCP~/iLEAPP-MCP, à côté du précédentServeur MCP (FastMCP) sur une sortie iLEAPP, branche feat/harness-provenance. Dépendance du harness par chemin relatif. Code : Wo0keyz/iLEAPP-MCP.
iLEAPP~/iLEAPPTraitement de l'image iOS en exports. Utilisé une fois par cas, en amont.
Langfuse~/langfuse-localCompose Docker de Langfuse v4, hors du dépôt (il contient des secrets).

Installation depuis une machine vierge

Les étapes suivent l'ordre des dépendances. Les commandes supposent Ubuntu (24.04 ou plus récent), un compte avec sudo, et un accès à Internet pendant l'installation : la machine n'est isolée qu'ensuite (étape 10).

1.Système de base

sudo apt update && sudo apt upgrade -y
sudo apt install -y git curl jq tmux openssl ca-certificates gnupg \
    python3 python3-venv python3-pip build-essential ufw iptables

tmux sert aux longues exécutions (une analyse ou une évaluation dure des heures) : elles survivent à la fermeture de la session SSH.

2.Pilote NVIDIA

sudo ubuntu-drivers list           # pilotes proposés pour la carte
sudo ubuntu-drivers install        # installe le pilote recommandé (ici la branche 595, « open »)
sudo reboot
nvidia-smi                         # doit afficher la carte et la version du pilote
Une mise à jour du pilote sans redémarrage laisse nvidia-smi en erreur (« driver/library version mismatch ») et empêche les conteneurs d'accéder au GPU. Redémarrer, puis relancer le serveur d'inférence.

3.Docker, Compose et accès au GPU

sudo apt install -y docker.io docker-compose-v2
sudo usermod -aG docker "$USER"     # puis se déconnecter / reconnecter

# NVIDIA Container Toolkit (dépôt officiel NVIDIA)
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey \
  | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list \
  | sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' \
  | sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt update && sudo apt install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# contrôle : un conteneur voit le GPU
docker run --rm --gpus all ubuntu nvidia-smi

4.uv et Python

curl -LsSf https://astral.sh/uv/install.sh | sh   # installe uv et uvx dans ~/.local/bin
source ~/.local/bin/env
uv python install 3.14                           # version de .python-version ; uv sync l'installerait sinon

5.Modèle GGUF

Le serveur d'inférence monte un fichier GGUF. Sur la machine de référence, le modèle a été récupéré avec Ollama, qui range chaque fichier sous un nom égal à son SHA-256 : le chemin du blob identifie donc le modèle. Ollama ne sert ici qu'à télécharger : c'est llama.cpp qui exécute le modèle.

curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen3.8:latest                       # Qwen3.8 27B, Q4_K_M, environ 17 Go
ls -lh ~/.ollama/models/blobs/sha256-68f0041ed409b99e3620d92c7693029361cef0fb3f13b141d61e25f5a9cd6818

# contrôle d'intégrité : l'empreinte doit être celle du nom du fichier
sha256sum ~/.ollama/models/blobs/sha256-68f0041ed409b99e3620d92c7693029361cef0fb3f13b141d61e25f5a9cd6818

Tout autre GGUF convient, à condition de reporter son chemin dans infra/llama.env, son alias dans MODEL_NAME, puis de rejouer l'évaluation : les chiffres publiés ne valent que pour ce modèle. Si Ollama tourne en service, l'arrêter pour libérer le GPU (sudo systemctl disable --now ollama).

6.Serveur d'inférence llama.cpp

Le serveur est décrit par deux fichiers versionnés : infra/docker-compose.yml (image épinglée par empreinte, port lié à 127.0.0.1, réservation GPU) et infra/llama.env (réglages, aucun secret). Ils ne peuvent être utilisés qu'une fois le dépôt du harness cloné (étape 9) ; l'ordre est ici celui des dépendances logiques.

MODEL_FILE=/home/<utilisateur>/.ollama/models/blobs/sha256-68f0041ed409b99e3620d92c7693029361cef0fb3f13b141d61e25f5a9cd6818
MODEL_ALIAS=qwen3.8:latest

# Contexte total, partagé entre les slots : 131072 / 4 = 32768 tokens par appel.
CTX_TOTAL=131072
PARALLEL=4

# RTX 3080 (10 Go) : 24 couches sur le GPU, le reste sur le CPU (≈ 3,5 tokens/s en génération).
GPU_LAYERS=24
THREADS=24
KV_CACHE_TYPE=q4_0

Le compose traduit ces variables en arguments de llama-server :

ArgumentValeurEffet
-m /models/model.ggufmonté en lecture seulele GGUF de l'hôte, toujours vu sous ce chemin dans le conteneur
--alias${MODEL_ALIAS}nom renvoyé par /v1/models, à reporter dans MODEL_NAME
--parallel4slots ; le harness ne fait jamais plus de LLM_PARALLEL appels simultanés
-c131072contexte total, divisé entre les slots
-fa on, -ctk/-ctv q4_0flash attention, cache KV quantifié sur 4 bits
-ngl, -t24, 24couches sur le GPU, fils CPU
-b 2048 -ub 512, --numa distributetailles de lot, répartition sur les deux sockets
--host 0.0.0.0 --port 8080dans le conteneurpublié sur l'hôte en 127.0.0.1:8080 uniquement : l'API n'a pas d'authentification
 
cd ~/forensic-langgraph
docker compose --env-file infra/llama.env -f infra/docker-compose.yml up -d
docker logs -f llama-server                      # chargement du modèle : plusieurs minutes

curl -s localhost:8080/v1/models | jq '.data[0].id'                         # "qwen3.8:latest"
curl -s localhost:8080/props | jq '.default_generation_settings.n_ctx, .total_slots'   # 32768, 4

Changer de version de llama.cpp, de modèle ou de réglage se fait dans ces fichiers versionnés, puis se mesure avec l'évaluation. Le script ~/start-llama-server.sh de la machine de référence ne fait que supprimer un ancien conteneur lancé à la main et appeler ce même compose.

7.Langfuse auto-hébergé

Langfuse reçoit les traces de chaque exécution et les expériences d'évaluation. Il garde son propre compose, hors du dépôt, parce qu'il contient des secrets. Partir du compose officiel :

mkdir -p ~/langfuse-local && cd ~/langfuse-local
curl -fsSLo docker-compose.yml https://raw.githubusercontent.com/langfuse/langfuse/main/docker-compose.yml

Puis, dans ce fichier :

  1. Remplacer chaque valeur marquée # CHANGEME par un secret propre : NEXTAUTH_SECRET, SALT, ENCRYPTION_KEY (64 caractères hexadécimaux), mots de passe de Postgres, ClickHouse, MinIO et Redis (et DATABASE_URL en cohérence). Les ranger dans un .env à côté du compose, en chmod 600.
  2. Épingler les images par empreinte (valeurs de la machine de référence, relevées le 2026-09-30) :
    langfuse-webdocker.langfuse.com/langfuse/langfuse@sha256:6efeeb58921a44fd043d8b3e47afd6fa9c221a1efc01333f68de7d20e4ca719b
    langfuse-workerdocker.langfuse.com/langfuse/langfuse-worker@sha256:8c3e33fc503c4e64992a933b248c60b5e409ad4c27c419d6c8f3a42782a44dba
    clickhousedocker.io/clickhouse/clickhouse-server@sha256:8a790dd3468db22b1d4e7b18a176f378ff5ff6053b9c48dd4ea1fa71a24c5ba6
    miniocgr.dev/chainguard/minio@sha256:bd014394a80898e68c149f2311fdf8d5a2c2f3bb2c33b9327ae6d02b4b065ae1
    redisdocker.io/redis@sha256:c6eabf748fc7a61dbb5a705c78bcf3d6377b1127a97d0ce965c11c44ba46896f
    postgresdocker.io/postgres@sha256:f4c66b820c6f974249089d3d16d86a3698eae11e8746eb6644b2271031e91232
  3. Vérifier les ports : seul langfuse-web (3000) est publié sur toutes les interfaces ; worker (3030), Postgres (5432), ClickHouse (8123, 9000), Redis (6379) et MinIO (9090, 9091) restent liés à 127.0.0.1.
  4. Mettre TELEMETRY_ENABLED=false (aucun appel sortant) et NEXTAUTH_URL=http://<HOTE_ANALYSE>:3000.
openssl rand -hex 32        # ENCRYPTION_KEY
openssl rand -base64 32     # NEXTAUTH_SECRET, SALT, mots de passe
docker compose up -d
docker compose ps           # tous les services « healthy » ou « running »

Depuis le poste de l'analyste, ouvrir http://<HOTE_ANALYSE>:3000, créer le compte, l'organisation et le projet, puis une paire de clés API (Settings → API Keys). Elles vont dans le .env du harness (Configuration). Les variables LANGFUSE_INIT_* du compose permettent aussi de créer organisation, projet et clés au premier démarrage, sans interface.

Conserver le .env de Langfuse à part et en lieu sûr : sans ENCRYPTION_KEY et SALT, une sauvegarde des volumes ne peut pas être déchiffrée. Sur la machine de référence, les mots de passe internes des bases sont encore ceux du compose officiel ; ces bases n'écoutent que sur 127.0.0.1, mais il faut les changer.

8.iLEAPP et traitement d'une image

git clone https://github.com/abrignoni/iLEAPP.git ~/iLEAPP
cd ~/iLEAPP
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

# le dossier de sortie doit exister avant le traitement
mkdir -p ~/cases/<cas>-iLEAPP_Output
.venv/bin/python ileapp.py -t tar -i /chemin/vers/extraction.tar -o ~/cases/<cas>-iLEAPP_Output

Types d'entrée : fs, tar, zip, gz, itunes, file, et raw pour une image disque (E01, dmg, img…). Le dossier attendu par le harness est celui qui contient _TSV Exports/, _lava_data.lava, _HTML/, _Timeline/, data/ et media/.

Ne jamais placer le dossier des exécutions (runs/) dans le dossier de preuves : le harness refuse de démarrer. Traiter les sorties iLEAPP comme des preuves : copie de travail, droits en lecture seule (chmod -R a-w) après le traitement.

10.Pare-feu et isolement

Deux scripts, à lancer avec sudo. Leurs règles ne survivent pas à un redémarrage : les relancer après chaque reboot.

# une fois, depuis la console ou une session SSH déjà ouverte
sudo infra/firewall.sh <IP_POSTE_ANALYSTE> <INTERFACE>

# avant un vrai dossier
sudo infra/airgap.sh on <RESEAU_LOCAL>
sudo infra/airgap.sh status               # doit répondre « Isolement ACTIF »
ping -c1 1.1.1.1                          # doit échouer

sudo infra/airgap.sh off                  # pour les mises à jour
ScriptCe qu'il fait
firewall.shufw : tout refusé en entrée sauf SSH depuis <IP_POSTE_ANALYSTE>. Puis une règle dans la chaîne DOCKER-USER qui rejette toute connexion au port 3000 venant d'une autre adresse sur <INTERFACE> : ufw ne filtre pas les ports publiés par Docker. Affiche enfin les ports TCP en écoute hors localhost (attendu : 22 et 3000).
airgap.sh onCrée une chaîne FORENSIC_AIRGAP branchée sur OUTPUT et DOCKER-USER, en IPv4 et IPv6 : seuls la boucle locale, 127.0.0.0/8, les réseaux internes de Docker (172.16.0.0/12) et <RESEAU_LOCAL> restent joignables ; tout le reste est rejeté. Appliqué entièrement ou pas du tout (piège EXIT).
airgap.sh statusVérifie les trois sauts (OUTPUT v4, DOCKER-USER v4, OUTPUT v6). Code de sortie 1 si l'isolement n'est pas actif.

Si le poste de l'analyste partage sa connexion Internet avec la machine (câble direct), c'est sur ce poste qu'il faut couper le partage : l'isolement laisse le réseau local joignable.

11.Vérification de bout en bout

cd ~/forensic-langgraph
uv run python -m forensic_harness.synthetic_case /tmp/synthetic-benign          # petit cas fictif
uv run python -m forensic_harness /tmp/synthetic-benign --plan                  # budget mesuré sur le serveur ?
uv run python -m forensic_harness /tmp/synthetic-benign --no-review             # exécution complète, environ 35 min
uv run python -m forensic_harness --verify runs/synthetic-benign/<UTC> --manifest-sha256 <empreinte affichée>

Attendu : --plan affiche « mesuré » (sinon le serveur d'inférence n'est pas joignable), le run se termine par l'empreinte du manifeste, une trace apparaît dans Langfuse, et --verify répond « Exécution intacte ».

Ligne de commande

uv run python -m forensic_harness CAS [--since DATE] [--until DATE] [--plan] [--no-review]
uv run python -m forensic_harness --resume EXÉCUTION --draft-sha256 EMPREINTE (--approve --analyst NOM | --reject --note MOTIF)
uv run python -m forensic_harness --verify EXÉCUTION [--manifest-sha256 EMPREINTE]
OptionEffet
CASDossier de sortie iLEAPP (ou CASE_PATH).
--planExtraction et mesure du budget, puis coût prévu par domaine (preuves, lots, tokens), sans appeler le modèle. À lancer avant tout gros dossier.
--since, --untilFenêtre de dates (ISO, UTC). Une date seule en fin de fenêtre désigne le jour entier ; les preuves sans date sont gardées ; une fenêtre illisible ou inversée est refusée.
--no-reviewPas d'arrêt avant le rapport (essais, évaluation) : le rapport porte « NON RELU PAR UN ANALYSTE ».
--resumeReprise d'une exécution en attente, depuis son point d'arrêt SQLite, sans rappeler le modèle. Exige --draft-sha256 et une décision. --approve exige --analyst ; --reject exige --note.
--verifyRecalcule les empreintes de l'exécution et du dossier de preuves ; liste les écarts. Avec --manifest-sha256, détecte aussi une réécriture complète.

Codes de sortie

CodeSens
0Rapport produit sans anomalie (ou --verify : exécution intacte).
1--verify : écarts trouvés.
2Rapport produit avec des anomalies, listées dans le rapport et sur la sortie d'erreur. Aussi : erreur d'arguments.
3Analyse faite, brouillon en attente de la décision de l'analyste.

Dossier d'exécution

Chaque exécution a son dossier runs/<cas>/<horodatage UTC>/, non versionné. Un dossier déjà utilisé n'est jamais réécrit.

runs/<cas>/20261003T070014Z/
├── manifest.json        empreintes des preuves et des livrables, versions, modèle, décision
├── manifest.sha256      empreinte du manifeste : à consigner hors de la machine
├── report.md            rapport final (après décision ou avec --no-review)
├── report.draft.md      brouillon soumis à validation
├── preuves.json         exactement les preuves citées par le rapport (P1…Pn)
├── findings.json        constats vérifiés et rejetés, mesures de chaque appel au modèle
├── extraction.json      toutes les preuves transmises, leur provenance, la couverture
├── tool_calls.jsonl     journal des appels au serveur MCP, empreinte de chaque résultat
├── budget.json          contexte mesuré sur le serveur d'inférence
├── llm/                 chaque prompt envoyé et chaque réponse brute (agent_n.prompt.txt, agent_n.txt)
├── run.json             durée, anomalies, identifiant de trace Langfuse
└── checkpoint.sqlite    point d'arrêt LangGraph pour la reprise

Le graphe LangGraph

Le graphe principal est construit dans forensic_harness/graph.py (build_graph) ; le sous-graphe d'enquête dans forensic_harness/investigate.py (build_enquete). langgraph.json expose le graphe compilé sous le nom profiling pour LangGraph Studio.

État partagé

State est un TypedDict. Les champs écrits par des branches parallèles portent un réducteur :

ChampRéducteurContenu
case_path, run_dir, since, until—Entrées et dossier d'exécution.
budget—Contexte mesuré : n_ctx, chars_per_token, measured.
resultsoperator.or_Par domaine puis hypotheses, qualification, redaction : verified, rejected, limits, calls…
enquetesoperator.addUne entrée par scénario : scénario, instruction, contradiction, verdict, tours.
errorsoperator.addAnomalies d'exécution, imprimées dans le rapport.
review—Décision de l'analyste, injectée à la reprise.
final_report—Texte du rapport.

Les preuves ne transitent pas dans l'état : elles restent sur disque (extraction.json), chargées par load_extraction et protégées par un verrou par dossier (evidence_lock) quand les enquêtes parallèles y ajoutent des lignes. L'état reste ainsi petit pour le point d'arrêt SQLite (AsyncSqliteSaver, checkpoint.sqlite).

Enregistrement d'une preuve

_record transforme chaque ligne renvoyée par le serveur. Une ligne sans provenance (evidence_id, source_file) fait échouer l'extraction. Les colonnes vides, les champs de provenance et les colonnes de chemin source d'iLEAPP sont retirés du contenu ; le premier champ dont le nom évoque une date (time|date|created|modified|install) donne l'horodatage, normalisé en UTC (une valeur sans fuseau est UTC, convention iLEAPP). Un champ de plus de MAX_FIELD_CHARS caractères est coupé, avec la mention …[coupé : n caractères de plus].

{
 "tag": "E412",                     # attribuée après lecture complète, dans l'ordre de lecture
 "uid": "EV-3f9a1c2b7d40",          # evidence_id du serveur
 "source_file": "_TSV Exports/…tsv",
 "source_table": null,
 "row_id": 18,
 "ios_path": "private/var/…",
 "digest": "c41e07b9d2a8f356",      # row_digest du serveur
 "ts": "2025-12-12T20:30:00Z",
 "fields": { "colonne": "valeur", … }
}

Les références E1…En sont attribuées dans l'ordre de lecture : même dossier et même code donnent les mêmes références. Une collision d'evidence_id (même identifiant pour deux emplacements) arrête l'extraction. Un artefact absent du dossier est noté absent, pas en erreur ; toute autre panne est consignée (status: "error") et signalée au modèle (« ne rien conclure sur cette source »), jamais transformée en liste vide.

Lots et compactage

domain_chunks découpe un domaine en lots d'au plus Budget.chunk_chars(…) caractères. Les messages sont regroupés par conversation (première colonne présente parmi Conversation With, Chat Name, Chat Contact ID, Conversation ID, Thread ID, Chat ID). Toute preuve figure dans exactement un lot ; une conversation trop longue continue au lot suivant. _compact réduit le texte sans rien retirer de citable :

  • une colonne de même valeur sur toutes les lignes d'une conversation (au moins 3 lignes) est écrite une fois en tête ;
  • des lignes consécutives identiques aux dates près sont réunies, avec toutes leurs références et toutes leurs dates ; une ligne à plusieurs dates, ou séparée par une autre, reste seule ;
  • les identifiants internes sont omis.

Gain mesuré sur Magnet : −8 % de texte. Les citations sont vérifiées contre le texte complet de la ligne (record_text : colonne=valeur ; …), pas contre le texte compacté.

Couverture

L'extraction garde la liste des exports du dossier qui n'ont pas été lus (unread, triés par nombre de lignes) : environ 200 sur Magnet. Ils sont accessibles à l'enquête et comptés dans la section « Portée et limites » du rapport, avec, source par source, les lignes totales, transmises, vides et hors fenêtre (coverage_table).

Appels au modèle

forensic_harness/llm.py. Le client est langchain_openai.ChatOpenAI pointé sur llama.cpp :

ChatOpenAI(
    base_url=url, api_key="not-needed", model=model,
    temperature=config.LLM_TEMPERATURE,        # 0.1
    seed=config.LLM_SEED,                      # 0
    max_tokens=max_tokens, timeout=config.LLM_TIMEOUT_S, max_retries=1,
    extra_body={"chat_template_kwargs": {"enable_thinking": False}},
)
  • Sortie contrainte. Chaque agent est lié à un response_format de type json_schema strict (prompts.response_format) : llama.cpp le compile en grammaire, et le modèle ne peut pas sortir de la forme {"findings": [...], "limits": "...", …}. Chaque référence doit correspondre à ^E[0-9]{1,7}$ ; les champs propres à l'agent (signal, sens, section, verdict…) sont des énumérations.
  • Raisonnement interne coupé. enable_thinking: false : pas de bloc de réflexion, toute la longueur de réponse va au JSON.
  • Slots. Un sémaphore par serveur (slot()) limite les appels simultanés à LLM_PARALLEL (ou READ_PARALLEL pour un serveur de lecture séparé), quel que soit le nombre de branches parallèles du graphe.
  • Aucun échec silencieux. Réponse vide, coupée à max_tokens (finish_reason == "length"), fin anormale ou serveur injoignable : l'exécution continue et l'anomalie va au rapport. Une réponse coupée garde ses constats complets (validate._load referme la liste après le dernier constat entier).

Un appel d'agent : run_agent

Cache des réponses

DiskCache (SQLite, WAL) garde les réponses complètes (finish_reason == "stop", texte non vide) des appels avec schéma : lecture, hypothèses, conclusions, rédaction. La clé est le SHA-256 de :

taille du GGUF | n_params | ftype | sha256(chat_template)[:16] | build_info     # lus sur /v1/models et /props
\0 paramètres de l'appel (llm_string)  \0 messages

Un autre GGUF sous le même alias ne relit donc pas les réponses de l'ancien. Les tours d'outils de l'enquête ne passent jamais par le cache (ils interrogent réellement le serveur de preuves). Un cache illisible, verrouillé ou plein est contourné, jamais une réponse perdue. LLM_CACHE= (vide) le coupe ; evaluate --runs N avec N > 1 le coupe d'office. Le rapport dit combien de réponses viennent du cache.

Budget de contexte

forensic_harness/budget.py mesure le contexte sur le serveur au lieu de le supposer : n_ctx par slot via /props, et le nombre de caractères par token via /tokenize sur un échantillon de 20 000 caractères de vraies lignes de preuve (environ 2 caractères par token sur des lignes pleines d'horodatages et d'identifiants, loin des 3 à 4 du texte courant). Avec un serveur de lecture séparé, le plus petit contexte et la tokenisation la plus dense des deux sont retenus.

room   = n_ctx − max_tokens − overhead_chars / chars_per_token − 0,05 × n_ctx
tokens = room                          si whole_context    # hypothèses, enquête, qualification, rédaction, condensation
       = min(CHUNK_TOKENS, room)       sinon               # lots de lecture
chars  = max(1000, tokens × chars_per_token)

Si la mesure échoue, le budget retombe sur CTX_TOKENS et CHARS_PER_TOKEN, et une anomalie est consignée. Quand un bloc de prompt ne tient pas, il est tronqué avec une mention explicite au modèle (« PARTIEL : n autres … ne t'ont pas été transmis ») et une anomalie au rapport.

Agents et prompts

Tous les prompts sont dans forensic_harness/prompts.py, source unique versionnée avec le code. L'empreinte de ce fichier et du catalogue (prompts.digest()) est consignée dans chaque manifeste. Deux régimes : la lecture est neutre (elle décrit, ne qualifie pas, ne sait pas ce que contient le dossier) ; l'enquête cherche activement ce qui pourrait être illégal, à charge et à décharge. Aucun prompt ne nomme un fait propre à un cas.

forensic_harness/validate.py, sans modèle. validate(findings, index, allowed) sépare vérifiés et rejetés ; un rejeté porte ses motifs dans reasons. allowed est l'ensemble des références effectivement transmises à cet agent.

Dates présentesdates du constat (ISO, « 12 décembre 2025 », 12/03/2025) ⊂ dates des preuves citées (ISO, anglais, 12/03/2025 lu dans les deux sens)

Auteur non contredit_author_contradiction : compare le champ auteur aux colonnes d'expéditeur (Author, Sender Name, Sender Email, From…) et de sens (Direction, From Me…) des messages cités. Rejet seulement en cas de contradiction nette : un message reçu attribué à l'utilisateur, ou un auteur qui n'est ni l'expéditeur écrit ni compatible avec le sens. Une direction numérique ambiguë (InteractionC) ne conclut rien

Normalisation commune (_norm) : NFKC, apostrophes et guillemets typographiques ramenés à leur forme simple, espaces et retours réduits, casse ignorée. La relance (rejection_feedback) renvoie au modèle chaque constat rejeté (200 premiers caractères) avec ses motifs.

Ce que le contrôle ne fait pas Il ne lit pas le sens. Il compare l'auteur déclaré aux preuves, pas le sujet grammatical de la phrase. Il ne filtre aucun terme accusatoire à l'exécution : les termes interdits ne sont mesurés qu'à l'évaluation (forbidden_terms des jeux témoins).

Contradiction et plafond

charge = [f for f in instr["verified"] if f["sens"] == "charge"]
if not charge:                                   # rien à contredire : pas d'appel
    verdict = "non_etaye"
...
if verdict not in prompts.VERDICTS:              # absent ou invalide
    verdict = "fragile"
distinct = {t for f in charge for t in f["evidence"]}

Qualification et rédaction

Catalogue

forensic_harness/qualifications_ch.json : droit suisse (CP et LStup), statut « PROJET : intitulés et éléments constitutifs résumés pour orienter l'analyse, à faire valider par un juriste avant tout usage. La qualification revient au magistrat. » Onze entrées : CP156, CP181, CP180, CP162, CP273, CP143, CP143bis, CP251, CP146, CP322octies, LStup19, chacune avec id, intitule, base et la liste de ses elements. Un autre droit se branche en fournissant un autre fichier (QUALIFICATIONS) de même forme ; son empreinte change celle des prompts.

Contrôles propres

  • qualification est une énumération des identifiants du catalogue dans le schéma JSON, et le numéro de scénario doit être celui d'un scénario retenu ;
  • seuls les constats etat == "etabli" sont des éléments soutenus ; les autres vont dans non_etablis (dans findings.json, pas dans le rapport) ;
  • un élément manquant n'est gardé que s'il recopie (après normalisation) un élément du catalogue pour une qualification soutenue, et s'il n'est pas déjà dit soutenu.

Rédaction

Le rédacteur reçoit le contexte, les scénarios retenus avec leur instruction et leurs objections, les qualifications envisagées, et la chronologie des preuves citées (cited_chronology). Sans aucune preuve à citer, il n'est pas appelé. S'il omet la synthèse, un second appel (SYNTHESIS_ONLY) la demande seule.

Clôture et contrôle

  • seal écrit outputs_sha256, puis manifest.sha256, puis passe fichiers et dossiers en lecture seule (0444/0555). La CLI affiche l'empreinte du manifeste : à noter hors de la machine.
  • verify recalcule tout : manifest.json contre manifest.sha256, contre l'empreinte notée (--manifest-sha256, préfixe accepté), chaque fichier contre outputs_sha256 (ajouté, supprimé, modifié), et le dossier de preuves contre tree_sha256.
  • Reprise (resume) : refusée si le brouillon sur disque n'a pas l'empreinte donnée, ou si l'état enregistré (constats, preuves extraites, manifeste) ne redonne plus ce brouillon. Le rapport final dit ce que disait le brouillon relu, avec la décision en tête.
  • Une exécution lancée depuis LangGraph Studio n'est pas clôturée : la clôture est faite par la CLI.

Serveur iLEAPP-MCP

Dépôt iLEAPP-MCP (paquet ileapp_mcp 0.2.0, FastMCP, Python ≥ 3.10, licence MIT), branche feat/harness-provenance. Le harness le lance par python -m ileapp_mcp.cli <cas> en transport stdio (forensic_harness/mcp.py, open_case), puis vérifie par get_case_info que le serveur sert bien ce cas, qu'il y a des exports, et que l'index n'est pas tronqué ; sinon l'analyse est refusée. Tous les accès passent par CaseSession.call, qui journalise outil, arguments, durée et SHA-256 du résultat canonique ; aucune erreur n'est avalée.

Garanties de lecture seule

  • bases SQLite ouvertes en URI file:…?mode=ro ;
  • run_readonly_sql : requêtes SELECT/WITH/EXPLAIN/certains PRAGMA seulement, une seule instruction, liste noire des mots-clés de mutation, puis le mode ro du moteur ;
  • exports TSV/CSV lus par le module csv en mode strict (utf-8-sig) : un fichier illisible fait échouer l'appel au lieu de passer pour un export vide ; les fichiers de l'appareil sous data/ ne sont pas indexés ;
  • indexation arrêtée à 2 000 000 d'entrées, signalée par index_truncated ;
  • la reprise automatique du dernier cas (ILEAPP_MCP_RESUME_LAST_CASE) est désactivée par défaut.

Provenance de chaque ligne

evidence_id = "EV-" + sha256(f"{source_file}|{source_table or ''}|{row_id}")[:12]

  • LangGraph Studio, en local uniquement : ./launch_studio.sh lance langgraph dev --host 127.0.0.1 --port 2024, sans tunnel (l'API de développement n'a pas d'authentification et lit des preuves). Accès distant par ssh -L 2024:localhost:2024 <HOTE_ANALYSE>.

Évaluation

forensic_harness/evaluate.py rejoue le graphe sur un cas (--case, --runs N) ou note des exécutions existantes (--score), contre un jeu de données (datasets/*.json).

Jeux de données

Règle de détection d'un fait (match) : une chaîne (mot entier, insensible à la casse et aux apostrophes typographiques), digits: (chiffres d'un même numéro, quels que soient les séparateurs), re: (expression régulière), ou {"all": [...]} / {"any": [...]}. Un scénario a un match sur sa description et un evidence_match sur les preuves citées. Un terme interdit nié dans sa proposition (« aucun », « pas », « sans »…) ne compte pas comme accusation. Les jeux ont été audités face aux sorties iLEAPP le 5 octobre 2026 (--audit) : exports cités corrigés pour Hickman, règles et termes interdits complétés pour les témoins.

Le script clone le dépôt dans runs/real/eval-<étiquette>[-variante]/frozen, se place sur l'étiquette, réutilise le .venv et le .env du dépôt, coupe le cache (LLM_CACHE=), génère les deux cas synthétiques, rejoue Magnet, Hickman (s'il existe), ambigu et bénin (ces deux derniers avec --gate datasets/gate_temoin.json), tient un journal.txt, et assemble RESULTATS.md. Pour compléter une campagne, on rejoue des exécutions supplémentaires dans le même clone figé, puis on renote ensemble tous les dossiers complets avec --score : c'est ainsi qu'a été obtenue la campagne publiée (voir Résultats).

evaluation.sh contient des chemins absolus de la machine de référence (dépôt sous /home/<utilisateur>/forensic-langgraph, Magnet sous /home/<utilisateur>/iPhone14Plus-CTF-MAGNET-iLEAPP_Output, Hickman sous /home/<utilisateur>/cases/iOS17-Hickman-iLEAPP_Output) : les adapter avant usage.

Langfuse

Avec les clés renseignées, push_langfuse inscrit chaque exécution notée comme expérience : Datasets → jeu → passage nommé d'après le dossier d'exécution, toutes les mesures en scores. Langfuse n'exécute rien : il range et compare. N'y partent que les mesures, les identifiants de faits et de scénarios, et les chemins.

Serveur de lecture MoE (facultatif)

La lecture des preuves fait l'essentiel des appels. Un second serveur peut la prendre en charge, sans toucher au serveur principal : Qwen3.6-35B-A3B (mixture of experts, 3 milliards de paramètres actifs par token), quantifié UD-Q4_K_XL par Unsloth, sur le CPU seul, même image llama.cpp.

# SHA-256 vérifié au téléchargement : 707a55a8a4397ecde44de0c499d3e68c1ad1d240d1da65826b4949d1043f4450
MODEL_FILE=/home/<utilisateur>/models/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf
MODEL_ALIAS=qwen3.6-35b-a3b
CTX_TOTAL=65536
PARALLEL=2
GPU_LAYERS=0
THREADS=24
docker compose --env-file infra/llama-moe.env -f infra/docker-compose.moe.yml up -d   # 127.0.0.1:8081
READ_LLM_URL=http://localhost:8081/v1 READ_MODEL_NAME=qwen3.6-35b-a3b READ_PARALLEL=2 \
    uv run python -m forensic_harness <cas>

Seules la lecture et sa condensation passent par ce serveur ; hypothèses, enquête, qualification et rédaction restent sur le serveur principal. Le budget de contexte prend le plus petit des deux serveurs ; le manifeste et l'en-tête du rapport décrivent les deux modèles. Ce réglage n'est pas celui des résultats publiés : il se juge avec infra/evaluation.sh <étiquette> 3 moe.

Limites connues et dépannage

Symptôme ou limiteCause, conduite à tenir
« budget de contexte non mesuré »Le serveur d'inférence ne répond pas sur /props ou /tokenize. Vérifier docker ps, docker logs llama-server et LLAMA_SERVER_URL.
« réponse coupée à n tokens »Le modèle a atteint max_tokens. Les constats complets sont gardés ; si cela se répète, réduire CHUNK_TOKENS.
« Index du cas tronqué » / « ce n'est pas une sortie iLEAPP »Mauvais dossier passé au harness : donner le dossier qui contient _TSV Exports/.
« dossier d'exécution déjà utilisé »Une exécution ne se réécrit pas : relancer crée un nouveau dossier horodaté.
Reprise refuséeEmpreinte du brouillon différente, ou état enregistré qui ne redonne plus le brouillon (code modifié entre-temps). Ne pas éditer le brouillon : le rejeter avec un motif et relancer.
Port 3000 joignable par d'autres postes après un rebootLa règle DOCKER-USER ne survit pas au redémarrage : relancer firewall.sh.
Isolement inactif après un rebootRelancer airgap.sh on puis status.
Sauvegarde de Langfuseinfra/backup-langfuse.sh arrête les services le temps de la copie (jamais pendant une analyse), archive chaque volume avec SHA256SUMS. Le .env de Langfuse n'est pas copié ; la restauration n'a pas été testée.
Reproductibilité au mot prèsNon garantie à température 0,1 et graine fixe : l'évaluation mesure la dispersion sur plusieurs exécutions.
Fichier du modèleIdentifié par son chemin ; un blob Ollama porte son SHA-256 dans son nom, le harness ne le recalcule pas.
Rendu de longue duréeLancer dans tmux : sur la configuration de référence, une exécution dure environ 6 h à l'horloge pour Magnet, environ 30 h pour un téléphone chargé comme Hickman.
